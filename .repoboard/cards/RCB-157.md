## Notes
- Filed 2026-09-26 from an open-source readiness review: a contributor's first PR must not fail on a flaky test.
- 2026-09-26 builder — MEASURED. (1) The failing test (store.test.ts, K8 hand edit) failed twice, both on the Node 24 CI job, both 'timed out after 4000ms waiting for card'; Node 22 passed on the same commits. (2) A truncate/write gap is not the cause: writeFile is open(O_TRUNC)+write, and a probe with a 0/50/150/400 ms gap between them (5 runs each, macOS) always delivered card:doing, at 106-171 ms (gap 0-50) and 276-528 ms (gap 150-400). (3) Linux in isolation (docker node:24-bookworm, 4 CPUs + 4 busy-loop burners): 40 of 40 runs passed, 520 K8 executions, 0 failures; the full suite with --coverage, 20 of 20 exit 0. (4) Starvation ruled out: in both failed CI runs the neighbouring watcher tests took normal times; only this one ran to the 4000 ms timeout. So the event was MISSED, not late, and raising the wait would not fix it. (5) chokidar 5.0.0's change filter passes any real write; not the hole.
- Side finding, separate bug, not yet its own card: a gap >= 150 ms between truncate and write makes the store read the empty file — removed + invalid(1), then card:doing with a file:CREATE ticker event instead of file:move.
- 2026-09-26 builder — an opt-in watcher DIAG hook landed: with REPOBOARD_WATCH_DIAG=1 (set on CI's test step) a waitForEvent timeout prints the store's raw/all/enq/run/ready/error/refresh rows. Not a fix.
- 2026-09-27 builder — CLASS 1, a test bug, FIXED. CI DIAG rows for 'a hand edit of status alone…' showed the store emitted at ~t+104 ms and the test attached waitForEvent only after 'await writeFile' resolved, too late. All 11 awaited waitForEvent sites in store.test.ts had that shape; all now create the wait before the trigger. Control: an injected 400 ms after the write passes with the new order and times out (4429 ms) with the old one. The ws-message queues in the systems/http/multiroot tests now dump DIAG rows on a timeout too.
- 2026-09-27 builder — CLASS 2, a product bug, FIXED by a periodic reconcile. macOS FSEvents loses events outright (local rows: ready only, no raw event). Probe: 65 of 1080 macOS trials missed with no raw event at EVERY delay after ready (0..2000 ms); Linux node 24, 0 of 1080. So a one-shot re-stat after ready would not cover it. The store now stats its tracked files every reconcileMs while watching (default 2000, 0 = off), routes a moved file through the watcher's router, leaves one 'sweep' DIAG row per sweep, and dedupes across sources so a change both the sweep and the watcher see emits once (with the dedupe disabled, a forced sweep-wins test emits twice, 3 of 3). CI green on Node 22 and 24 after it. Default: A (on at 2 s), pending the owner's pick; changing it is one line (load(): watch ? 2000 : 0).
- Still open, both measured, neither explained: (1) one full-suite failure in 4 of the new test 'watch: true, reconcileMs: 100 — a systems.yml write is reported once' (0 of 15 isolated idle, 0 of 15 with 16 CPU burners); the failing value was not captured. (2) one Linux CI miss on 'a file edit broadcasts systems' after the reconcile landed (rows: ready only); the sweep row now says whether the sweep ran, so the next miss will tell. That the cross-source dedupe fixed (1) is NOT shown.
