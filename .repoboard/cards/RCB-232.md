## Problem

Reported 2026-10-21 by a member board's coordinator. They ran `repoboard systems detect --apply --root` on a scratch
copy of a 12-detected-row `systems.yml`, and the real file was not touched.

1. **Runtime is lost.** On every UPDATED detected row (`source.detected`), `runtime.dev` and `runtime.prod`
   become the candidate's value, which is mostly `null`. One example: a row's dev runtime had hand-added
   text describing how the service runs locally and which local port it connects to, and `--apply`
   replaced it with null. In `applyDetected` (core `systems-detect.ts` ~1567), the updated-row object keeps
   `owner`, `docs`, `why` (`existing ?? cand`), `status` and `unblockedBy`, but takes `runtime`, `name`, `kind`,
   `layer` and `env` from the candidate. Hand rows (`source.hand`) are skipped, as designed.
2. **The layout is lost.** The whole file is re-serialized from flow style (`[dev, prod]`, quoted
   strings) to block style, so a one-pointer change shows as a ~600-line diff.

## Wanted

- An update merges only the fields detection owns: `pointers` and `source.detected/at`. Runtime is
  per env `existing ?? cand`, the same rule as `why`, so a detector can fill a null but never
  overwrite text. Decide in the brief whether `name`, `kind`, `layer` and `env` get the same treatment,
  and measure which of them the detectors actually change between runs.
- A no-op `--apply`, where nothing is detected that differs, leaves the file byte-identical. A one-row change
  touches only that row's lines. That likely means editing through the `yaml` Document API, not a
  `serializeSystems` round trip. Measure the diff size before and after on a flow-style fixture.
- The help text "never overwrites a hand row" stays true, and gains "never overwrites hand text
  on a detected row".
