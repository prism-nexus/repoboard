## Locked decisions (build them; CORRECT the brief in §7 if a measurement contradicts one)

1. **File:** `.repoboard/leases.yml`:
   ```yaml
   leases:
     - resource: vitest-lock        # free string, the team's name for the thing
       holder: claude/ops           # actor string, same hashing as assignee (D8)
       since: 2026-09-17T18:50:00Z
       until: 2026-09-17T19:30:00Z  # optional; absent = until released
       note: cold4 gate             # optional
   windows:
     - resource: vitest-lock
       start: 2026-09-17T18:50:00Z
       end: 2026-09-17T19:30:00Z
       name: cold4 gate
   ```
   Unknown keys kept on round-trip (like cards). Absent file = no leases, no windows. Timestamps ISO
   UTC with seconds.
2. **Semantics:** a lease with `until` in the past is **STALE** — reported as such, never silently held
   and never silently dropped (the holder may have died; a human decides). `lease take` on a resource
   with a live lease held by ANOTHER holder → `{ok:false, error}` naming the holder and `until`
   (`--force` overrides and writes an event saying so); same holder → renews (`since` kept, `until`
   replaced). `lease release` by a non-holder → error naming the holder (`--force` again). A window
   whose `end` is past is pruned on the next WRITE of the file (never on read — reads are pure).
3. **`window check <resource> [--at <ts>]`:** exit 0 and print `clear <resource>` when no window
   contains now (or `--at`); exit 1 and print the window (`inside <name> <start>–<end> <resource>`)
   when one does; a live lease on the resource by someone else ALSO makes it exit 1 with `held by
   <holder> until <until|—>`. This is what a lock shim calls. Exit 2 is a crash, as everywhere.
4. **Core (pure, `packages/core/src/leases.ts`):** `LeasesSchema`, `parseLeases(text)`,
   `serializeLeases(doc)`, `takeLease(doc, input, {now, actor, force})`, `releaseLease(...)`,
   `addWindow(doc, w)`, `pruneWindows(doc, now)`, `checkResource(doc, resource, at) → {clear:true} |
   {clear:false, reasons:[…]}`, `staleLeases(doc, now)`. Each mutation returns `{ok, doc, event,
   warnings}` or `{ok:false,error}` — the `moveCard` shape. Purity test stays green.
5. **Server:** the store watches `leases.yml` (re-read on change). `CardStore` gains `leases()`,
   `takeLease`, `releaseLease`, `addWindow`, `checkResource(resource, at?)`. Events: `type:
   'lease' | 'window'` with `resource` on the event (widen `Event` as P8.1 did for decisions — follow
   its pattern exactly). Map-only roots refuse writes.
6. **CLI:** `repoboard lease take <resource> [--as h] [--until ts] [--note n] [--force]` → `took
   <resource> as <holder> until <until|—>`; `lease release <resource> [--as h] [--force]`; `lease list
   [--json]` → table `RESOURCE HOLDER SINCE UNTIL STATE(live|stale) NOTE`; `repoboard window add
   <resource> <start> <end> <name>`; `window list [--json]`; `window check <resource> [--at ts]` per 3.
   Accept `--until` and window times as ISO **or** `+90m` / `+2h` relative to now (state which in
   AGENTS.md).
7. **MCP:** `take_lease`, `release_lease`, `list_leases`, `add_window`, `check_window` — same
   formatter as CLI `--json`, byte-identical. Descriptions for an agent that has never seen the board,
   including: "Call `check_window` before starting any long-running shared-resource job such as a test
   suite; exit/clear false means DO NOT start."
8. **HTTP:** `GET /api/leases` (the whole doc + `stale` ids + `now`), `POST /api/leases/take`,
   `/release`, `/windows`; `GET /api/leases/check/:resource?at=`. WS snapshot carries `leases`.
9. **Web:** a **Now** strip directly under the TopBar, on every view: `holding: vitest-lock ·
   claude/ops · until 19:30Z (stale ×1)` · `next window: cold4 gate 18:50–19:30Z vitest-lock` · nothing
   held → the strip collapses to one quiet line "no leases, no windows". Stale leases in the warning
   color. No modal, no fun (D9).
10. **Bytes (O3):** fixture with 3 leases + 4 windows: `lease list` table, `--json`, MCP `list_leases`
    result, MCP schema growth. Into `docs/AGENTS.md` §9 "Leases and windows" and your §7.

### Corrections to the brief, with the measurement that forced them

- **`EVENT_TYPES` in `store.ts`'s `parseEventLines` was missing `'ask'`/`'decide'`** (P8.1's own
  types), not just lacking `'lease'`/`'window'`. Measured: `appendEvent` pushes the event object
  it is given straight into `this.eventLog` regardless of type, so a live process never notices;
  only a REREAD (initial `load()`, a restart, or catching up on a line another process appended)
  runs a line through this filter, and `ask`/`decide` lines were silently dropped there since
  P8.1 shipped. Not filed as a separate item — fixed in the same one-line set I had to touch
  anyway to add `'lease'`/`'window'`, and noted here because leaving it half-fixed (add the two
  new types, leave the old gap) would have been a worse state than either doing nothing or fixing
  it outright.
- **`takeLease`'s "take fresh" path had a real bug the tests caught**: filtering `doc.leases` by
  `l !== existing` before pushing the new entry left a STALE entry behind when `existing` was
  `undefined` (a stale lease is not "live", so `liveLeaseOn` returns nothing for it) — the
  resource ended up with two rows. Measured via the `describe('takeLease')` test "a stale lease
  is taken fresh, no conflict, no force needed", which failed on `toEqual([{one entry}])` with two
  entries back. Fixed by filtering on `l.resource !== input.resource` instead of on `existing`'s
  identity — one entry per resource, always.
- **The two MCP tool "actor" descriptions had to be shortened, not just written terse from the
  start.** First pass reused patterns similar to P8.1's long `ACTOR_DESC` and left `take_lease`
  at 947 B and `add_window` at 734 B — over the orchestrator's 700 B aim. Measured via
  `client.listTools()` + `Buffer.byteLength(JSON.stringify(tool))`; cut the per-tool description
  text and introduced a short `ACTOR_SHORT` string used only by the five P8.2 tools, bringing all
  five to 691/509/400/630/645 B.
- **A real, pre-existing watcher flake, not something this task introduced.** The first version
  of the "external sed edit of leases.yml is re-read by the watcher" test created `leases.yml`
  fresh (it did not exist before the watcher started) and timed out intermittently once other
  test files were running concurrently. Isolated with a throwaway concurrency harness (20 stores
  opened at once): a **plain card-file `add`** under the SAME concurrency reproduces the identical
  timeout — this is chokidar's `add`-event detection under load in this sandbox, not a P8.2 defect.
  Confirmed the fix: modifying a file the fixture already wrote (a `change` event, not `add`) is
  reliable at 20 concurrent stores in the same harness, matching every OTHER "external edit" test
  in this file (they all edit a pre-existing card file). Rewrote the test to pre-write an empty
  `leases: []\nwindows: []\n` before opening the watching store, then edit it — same pattern as
  the rest of the suite, not a special case. Left named here rather than filed as a K-issue
  because it is this sandbox's chokidar/fsevents behavior under concurrent watcher startup, not
  a product defect a user would hit (a real repo has exactly one watcher).
- **Locked decision 7's `>=` wording for C3** reads as "make stale detection use `>=`"; the actual
  code compares `until < now` for staleness, so the perturbation that flips the boundary the way
  the control demands is `until <= now` (stale), not a literal `>=`. Implemented as `<=` and
  documented the reasoning in the perturbation comment — same boundary flip, the wording in the
  brief describes the complementary (live) condition's operator, not the stale one's.

### Left as named (not done, on purpose, and why)

- **No `--as`/actor flag documented for `window add` in the brief's own usage line**, but the CLI
  accepts one anyway (`repoboard window add <resource> <start> <end> <name> [--as a]`) — every
  other mutating CLI command in this repo takes `--as`, and `addWindow`'s event needs an actor
  regardless; omitting the flag would have meant every hand-added window is attributed to the
  default actor chain (`$REPOBOARD_ACTOR`/`$USER`/`cli`) with no way to say otherwise. Documented
  in `docs/AGENTS.md` §9 and the CLI `--help` text.
- **No overlap check on `addWindow`** — the brief's core function list does not ask for one, and
  the plan text says "No overlap check against other windows" explicitly (plan §5 P8.2). Two
  windows on the same resource with overlapping times are both kept; `checkResource` still
  reports every window that covers `at`, so an overlap is visible in the reasons list even though
  it was never rejected at write time.
- **`window check`'s reasons are printed one per line when both a window AND a live lease block
  the same resource** — the brief's own examples show each in isolation; when both apply, the CLI
  prints both lines and still exits 1 (tested implicitly by `checkResource`'s "a live lease also
  makes it not clear" test producing a `reasons` array of length 1 in the tested cases; the
  multi-reason path is exercised by `core`'s `CheckResourceResult` type but has no test forcing
  BOTH a window and a lease to fire at once — left as a gap, since the exit-code contract (0 vs 1)
  is unaffected either way and that is the part a lock shim actually reads).
- **Web mock data/demo (`packages/web/src/mock/data.ts`, `mock/index.ts`) updated** even though
  not in the brief's DoD, matching the P8.1 precedent of keeping the dev-preview mock current
  rather than stale: `mockLeases()` returns one live lease with a note, one stale lease, and one
  upcoming window, wired into the mock transport's snapshot so `VITE_MOCK=1 pnpm dev` shows the
  Now strip doing something, not just the quiet line.
- **`GET /api/leases/check/:resource` is always 200**, including `{clear:false}` — this was a
  judgment call the brief did not spell out explicitly (it lists `check` under the CLI's 0/1 exit
  contract, but HTTP has no exit code to carry the same meaning). Chose 200 because `{clear:
  false, reasons}` is a well-formed ANSWER to a read, not a failure of the request — mirrored
  after `board_summary`'s `wipBreaches` (a warning-shaped result, still 200), not after the
  ask/decide 409-on-conflict pattern (which is for a WRITE that cannot proceed, not a read that
  found something).
