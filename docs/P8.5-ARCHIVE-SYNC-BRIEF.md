### The heading-section function: reused, not duplicated

`refs.ts`'s `resolveRef`'s `'heading'` case used to compute `[start, end]` inline. I extracted
that exact logic into `findHeadingSection(lines, heading)` (same file), and rewired `resolveRef`
to call it — so `sync-issues` (`packages/server/src/issues.ts`) and K7's `path#Heading` refs share
ONE implementation of "what is the section under a heading", not two copies that could drift
(species 6's own lesson, applied as an architecture choice, not a comment). The refactor is
behavior-preserving: `packages/core/test/refs.test.ts`'s existing suite passed unchanged (24
tests, same file, no edits) both before and after.

One deliberate divergence from K7's ref resolution: `findHeadingSection` returns line INDICES
only, with no `span()` call — no `REF_MAX_LINES`/`REF_MAX_BYTES` truncation. A card's rendered
`refs:` preview is capped on purpose (200 lines / 16 KB) so the drawer stays readable; a K-list
section can be 3,000+ lines, and truncating it would have silently dropped most of freshpickedjobs'
real entries. This is not a bug in K7's cap — it is the reason `sync-issues` does not go through
`resolveRef`/`span()` at all, only through the shared section-finder underneath it.

3. **Title computation on a leading `.`**: the brief left open how to handle `- **K1. A full
   sweep…` (period immediately after the number). Chosen: strip a leading run of `.`/whitespace
   characters from the text after `**K<n>`, so the title reads `K1 A full sweep…` — never `K1 .
   A full sweep…` or `K1. A full sweep…`. Verified against the real fpj text via the identical
   K-list match above (had the period-stripping been wrong, titles would differ but the CREATE
   LIST OF NUMBERS would not — so this correctness claim rests on `core/test/issues.test.ts`'s
   hand-computed title assertions, not on the fpj match, which only proves the NUMBERS are right).
4. **`closeSyncedCard` is a new core function, not a call to `moveCard` with a different log
   line appended after**: `moveCard` always writes its own generic `moved <from> → <to>` line;
   there is no parameter to swap that text for `synced: entry closed in <path>`. Appending a
   SECOND log line after `moveCard`'s own would have produced two lines per synced close, which
   the brief's own wording ("move it … with log …") reads as ONE line, not two. Built as a
   sibling function in `packages/core/src/issues.ts` that mirrors `moveCard`'s shape (same event
   type `'move'`, same WIP-warning check) but writes only the custom line. Noted as a design
   choice, not a brief error.
5. **K10's store-structure tests** (`packages/server/test/store.test.ts`, "every method returning
   a `*Outcome` goes through `this.mutate`" and "nothing else in the store writes to disk") are
   pre-existing structural guarantees from P8.1/P8.2, not named in this brief — but `archiveCards`
   and `closeSynced` are new `*Outcome`-returning store methods, so both tests needed their
   enumerated-name lists extended (`archiveCards`, `closeSynced` added, alphabetically, and the
   `mutate` count widened from 11 to 13). The archive directory's `mkdir` was moved out of
   `store.ts` entirely and into `archive.ts`'s `archiveMoveFile` (which creates its destination
   directory before moving into it) specifically so `store.ts` gained no NEW raw `writeFile`/
   `rename`/`mkdir` call outside the five (now conceptually still five — the sixth "disk write" is
   in a different file, never scanned by that regex) already-guarded writers — the alternative
   (a sixth guarded writer method in `store.ts` just for the archive directory) was rejected as
   more surface than the guarantee needs, since `archiveMoveFile` already starts with `mkdir` as
   its own first act and is unreachable from any code path but `archiveCards`, which itself starts
   with `this.refuseWriteWithoutBoard()`.
6. **`card show` on an archived id**: implemented only on the CLI (`archived:
   .repoboard/archive/<id>.md`, per the brief's literal DoD line). HTTP `GET /api/cards/:id` and
   MCP `get_card` still return a plain "unknown card" 404/error for an archived id — the brief
   only named the CLI surface for this, and adding it to the other two would have meant inventing
   a new response shape neither surface has today. Left as a scope note, not fixed silently.
7. **HTTP status codes for archive/sync-issues**: `POST /api/archive` and `POST
   /api/sync-issues` are NOT unconditionally 200 the way `/api/cost` and `/api/leases/check/:r`
   are (those are pure reads even on their "real" path; these two can write). A real
   `sync-issues` call's per-item failures are collected into an `errors: string[]` in a 200 body
   rather than surfaced as a batch HTTP status, because the operation touches N cards at once and
   no single status code fits a partial failure — the same reasoning HTTP already uses for
   `warnings` on `/api/leases/take`. Noted as a design choice; not asked for explicitly.
