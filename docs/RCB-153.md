## 0. Why (the owner's question, answered)

The coordinator seat coordinates three repos from now on — freshpickedjobs, this one, and a new repo
the owner is creating — and it has been doing two of them from inside freshpickedjobs by a hardcoded
path to this repo's CLI (`node ~/projects/repos/remember-connect-build/packages/server/dist/cli.js`).
The cross-project decisions (the 0.2.0 release gate, the vitest-lock priority, the launch review) are
rows in freshpickedjobs' `docs/OWNER-DECISIONS.md` marked "cross-project, his word heard here". With a
third repo the record of what the owner decided would live in whichever repo the seat started in.

The seat's cold start is three reads: STATE, today's log, the decisions file. So the seat can only
move up if its record moves with it, and repoboard has to give a seat above the repos the same verbs
it has inside one. That is this card. It is also the first feature a user with two repos hits.

## 2. Decisions — locked, with the reasoning

**W1. A workspace is a normal board whose `board.yml` lists member boards.** New optional key:

```yaml
name: fpj-workspace
prefix: WS
repos:
  - key: freshpickedjobs          # the key the CLI, MCP and /api/repos use; must match /^[a-z0-9][a-z0-9-]*$/
    root: ../freshpickedjobs      # relative to THIS board's root, or absolute; `~` expanded
    writes: cards                 # optional; absent = read-only member (O7). Only value in v1: `cards`
  - key: repoboard
    root: ../Remember-Connect-Build
    writes: cards
  - key: <new-repo>
    root: ../<new-repo>
```

Why one file: §2 of the plan is the contract agents see; a second file is a second thing to learn.
Why a normal board: the coordinator's own cards, STATE.md, log, leases and gate ledger live there
unchanged — every existing verb works on the workspace's own record with zero new code. A board
without `repos:` is exactly today's board: **no existing test may change** (that is the regression
control for every slice).

**W2. The workspace root is a SIBLING repo, never the parent directory.** The owner's parent
(`~/Projects/Repos`) holds his live job search (`Job Seeker/…`, never written) and other private
repos; a git repo or a `.repoboard/` at that level is out. So `findRoot` needs no change: a seat
whose cwd is the workspace repo finds the workspace board; a seat inside a member finds the
member's board first. Per-repo seats are untouched. (How the coordinator's Claude Code session gets
read access to `../<member>` is `permissions.additionalDirectories` in the workspace's
`.claude/settings.json` — the owner's setup, not repoboard's.)

**W3. Members are resolved lazily, read-only, and a missing member is a finding, not a crash.**
`Store` (or a thin `Workspace` beside it) opens a member's store on first use, memoised, exactly
like `RepoRegistry`. Opening a member creates NOTHING in it (no `.repoboard/local`, no log dir, no
gate file). A `root` that does not exist or has no `.repoboard/` → `check` finding
`workspace-member-missing` (error) naming the key and path; `state` prints the key with `(missing)`.

**W4. Card ids resolve across the workspace by PREFIX.** At a workspace root, `FPJ-86` resolves to
the member whose `board.yml` prefix is `FPJ`; the workspace's own prefix is checked first; a prefix
two members share is an error naming both keys and asking for `key:ID` (`freshpickedjobs:FPJ-86`),
which is always accepted. Why prefix, not key: every human and every log line already says
`FPJ-86` / `RCB-51`; making the seat type `freshpickedjobs:FPJ-86` daily is the kind of cost the
handoff-economy review was about. Applies to: `card show/note/move/ask/decide/update`, `gate <id>`
values on WORKSPACE cards, MCP `get_card` etc.

**W5. Reads aggregate; writes need `writes: cards`.** At a workspace root:
- `state` renders the workspace's own stored sections (LIVE, LAST LANDINGS, SEATS) as today, and the
  GENERATED sections aggregate: OWNER QUEUE = the workspace's decide cards, then each member's,
  each line prefixed `[<key>]`; LEASES = the workspace's live leases then each member's, prefixed.
  `--json` adds `repos: { <key>: { ownerQueue, leases, missing?: true } }`. `--set-section` and
  `--trim-landings` write the workspace's own STATE.md only.
- `check` runs `checkFindings` for the workspace, then for each member (member log dirs, leases,
  gate ledger read in place), prefixes each finding `[<key>]`, exit code = the worst. A member's
  `local-no-remote` info is still just info.
- `card list` = the workspace's own cards; `--repo <key>` one member; `--repo all` every board with
  a `REPO` column first. `card show <id>` resolves by W4.
- Card WRITE verbs (`add` needs `--repo`; `move`, `note`, `ask`, `decide`, `update`) on a member
  card write that member's card file and append to that member's `events.jsonl` through that
  member's own `Store` and file lock — and refuse with `member <key> is read-only (set writes: cards
  in board.yml)` when `writes:` is absent. Nothing else in the member tree is touched: not its
  STATE.md, log, leases, gate ledger, `local/`. Why the opt-in: O7. The owner listing a repo is
  consent to READ it; `writes: cards` is the explicit ask to write.
- `lease`, `log`, `seat`, `gate`, `decisions`, `archive`, `local`: the workspace's OWN store only
  (a seat's record lives where the seat lives). `lease list` and `log show --repo <key>` may READ a
  member. No cross-board lease in v1: the fpj lane lease stays in fpj, taken by fpj seats.

**W6. `serve` at a workspace root with no `--root` serves the workspace plus every member**, roots
in `board.yml` order, keys from `repos[].key` (they replace `assignRepoKeys` for members; the
workspace itself is the primary and keeps its basename key). So `:4242` becomes
`repoboard serve --port 4242` run from the workspace, and the hand-typed two-root line in RIG.md
retires. Explicit `--root` flags still work exactly as today (no workspace expansion when any
`--root` is given — the flag is the override).

**W7. MCP: same store, same resolution, same 30 tools.** `repoboard mcp` at a workspace root opens
the workspace with its members. `list_cards`, `board_summary`, `check`, `get_state`, `list_leases`,
`get_log` gain an OPTIONAL `repo` argument (a key, or `all` where a list makes sense); the card
tools resolve ids by W4; write tools obey `writes: cards`. No new tool. The tool-count pin stays
30; the RCB-129/131 replay goldens are re-recorded only if a schema they cover changed, and the
diff of each re-recorded golden is pasted in the report.

**W8. `init --workspace --repo <key>=<path> …`** scaffolds `board.yml` with `repos:` (paths written
relative when under the same parent), and with `--practices` the usual STATE.md/log/leases. It
refuses to run in a directory that already has a `.repoboard/`, and it never touches the members.

**W9. Not in this card:** a workspace view in the web UI beyond what W6 gives the existing switcher
(a cross-repo owner-queue page is its own card once the owner has used the CLI one); cross-repo
`--ref`; cross-board leases; `cost` across members; moving the freshpickedjobs coordinator record
(that is a freshpickedjobs card the coordinator files when this lands: freeze the fpj cross-project
decision rows, redirect CLAUDE.md, copy the seat memory).

## 4. Controls — named by the test that must FAIL, and watched failing

Fixtures: `makeTempRepoboard` ×2 as members (`prefix: AA`, `prefix: BB`, one decide card each, one
live lease in AA) + a workspace temp board whose `board.yml` lists both, BB with `writes: cards`.

1. **Aggregation** — `state` at the workspace lists `[aa] AA-1` and `[bb] BB-1` under OWNER QUEUE
   and AA's lease under LEASES. Control: with the member loop reverted (or `repos:` emptied) the
   assertion FAILS; a plain board's `state` output is byte-identical to before (snapshot from
   `main` @ baseline — record the sha).
2. **Read-only members** — after `state`, `check`, `card list --repo all`, `card show AA-1` and
   `serve` (one request to `/api/repos/aa/…`) at the workspace, a recursive listing + mtimes of both
   member trees is IDENTICAL to before (`.repoboard/local/`, `log/`, `gate.jsonl`, `leases.yml`
   included). Control: a deliberate `mkdir` of `local/` in the open path must make this FAIL.
3. **Write opt-in** — `card note AA-1 "x"` at the workspace REFUSES with the exact text in W5 and
   AA's tree is unchanged; `card note BB-1 "x"` writes `BB-1.md` and appends ONE line to BB's
   `events.jsonl` and touches nothing else in BB (listing diff = those two paths). Control: remove
   the `writes:` check and the refusal assertion FAILS.
4. **Prefix resolution** — `card show BB-1` resolves; two members sharing `prefix: AA` → error text
   names both keys and `aa:AA-1` still resolves. Control: a workspace card with prefix `AA` wins
   over the member (workspace-first), asserted.
5. **Missing member** — a `repos:` entry pointing at a nonexistent path → `check` exit 1 with
   `workspace-member-missing`, `state` still renders with `(missing)`. Control: `check` on the same
   fixture with the entry removed exits 0.
6. **Gate across boards** — a workspace card `gate: BB-1` is `blocked` while BB-1 is todo and
   `clear` after `card move BB-1 done` (through the workspace, W5). Control: gate `ZZ-9` stays
   "no such card".
7. **Serve** — `serve` from the workspace with no `--root`: `GET /api/repos` = `[workspace, aa,
   bb]` with the configured keys; with an explicit `--root .` only the workspace is listed. Uses the
   `multiroot.test.ts` helpers.
8. **MCP** — `list_cards {repo:"bb"}` returns BB's cards; tool count still 30 (the existing pin).
9. **Regression** — the full suite: every pre-existing test unchanged in content (`git diff --stat
   -- packages/*/test` shows only the new file and additive lines in files you name), count ≥ 1590.
